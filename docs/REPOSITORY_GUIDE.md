# Как устроен репозиторий `ml-lab`

Этот файл объясняет, **зачем существует каждая папка и каждый основной файл**. Цель — чтобы структура проекта не была набором непонятных каталогов, а отражала нормальный рабочий ML-процесс.

---

# Общая идея структуры

Проект разделён на несколько уровней:

```text
данные
  ↓
исследование в notebooks
  ↓
переиспользуемый код в src
  ↓
тесты
  ↓
автоматическая проверка через GitHub Actions
```

То есть notebook нужен, чтобы **исследовать и экспериментировать**, а `src/` — чтобы постепенно переносить туда уже нормальный, переиспользуемый код.

# `.github/`

Это служебная папка GitHub.

Она не относится напрямую к ML-модели. В ней лежат настройки того, что GitHub должен делать автоматически.

## `.github/workflows/tests.yml`

Это конфигурация **GitHub Actions**.

GitHub Actions — встроенная автоматизация GitHub.

Сейчас workflow делает примерно следующее:

1. замечает новый push или pull request;
2. поднимает чистую виртуальную машину Linux;
3. скачивает репозиторий;
4. устанавливает Python 3.11;
5. устанавливает зависимости из `requirements.txt`;
6. запускает:

```bash
pytest -q
```

Зачем это нужно:

> код может работать у тебя на компьютере, но это ещё не означает, что проект действительно воспроизводим.

GitHub Actions проверяет проект на отдельной машине.

Позже сюда можно добавить:

- линтер;
- проверку форматирования;
- type checking;
- сборку Docker;
- ML-тесты;
- deployment.

# `data/`

Здесь находятся данные.

## `data/raw/`

**Raw = сырые данные.**

Сюда кладётся информация в том виде, в котором мы её получили.

Примеры:

```text
load_2026.csv
weather.csv
generation.csv
prices.csv
```

Очень важное правило:

> сырые данные стараемся не изменять вручную.

Если CSV пришёл от источника, он должен остаться таким же. Все преобразования делаются кодом.

Сейчас `sample_load.csv` создаётся командой:

```bash
python scripts/generate_sample_data.py
```

Сам CSV в GitHub не хранится, потому что `.gitignore` исключает содержимое `data/raw/`.

### Что такое `.gitkeep`

Git сам по себе не умеет хранить пустые папки.

Поэтому файл:

```text
data/raw/.gitkeep
```

практически пустой и существует только затем, чтобы папка `raw/` присутствовала в GitHub.

---

## `data/processed/`

**Processed = обработанные данные.**

Например из исходного файла:

```text
timestamp, load
```

мы можем получить:

```text
timestamp
load
temperature
hour
day_of_week
is_weekend
lag_1
lag_24
lag_168
```

И сохранить результат в:

```text
data/processed/features.csv
```

То есть:

```text
raw
 ↓
очистка / преобразования / feature engineering
 ↓
processed
```

В реальных ML-проектах разделение raw и processed очень полезно.

## `docs/FORECASTING_PROBLEM_TEMPLATE.md`

Шаблон постановки ML-задачи.

Перед тем как обучать модель, нужно ответить:

### Target

Что именно прогнозируем?

Например:

```text
электрическая нагрузка через один час
```

### Prediction horizon

Насколько далеко прогнозируем?

```text
1 час
24 часа
7 дней
```

### Features

Какие признаки доступны модели?

### Baseline

С каким простым решением сравниваемся?

### Metrics

Как измеряем качество?

### Validation

Как тестируем модель без подсматривания в будущее?

### Risks

Какие есть риски:

- leakage;
- выбросы;
- пропуски;
- смена распределения.

Это очень важная привычка.

**ML начинается не с `model.fit()`, а с правильной постановки задачи.**

# `notebooks/`

Здесь находятся **Jupyter Notebook**.

Notebook удобен для исследования данных, потому что позволяет смешивать:

- Python-код;
- графики;
- таблицы;
- формулы;
- текстовые выводы.

## `notebooks/01_eda.ipynb`

Первый notebook проекта.

EDA означает:

> Exploratory Data Analysis — исследовательский анализ данных.

Ты будешь использовать его примерно так:

```python
df.head()
df.info()
df.describe()
```

потом:

```python
df["load_mw"].mean()
```

потом графики и выводы.

### Почему всё не писать в notebook?

Поначалу можно экспериментировать:

```python
def some_feature(...):
    ...
```

Но если функция оказалась полезной и используется постоянно, её лучше вынести в:

```text
src/
```

То есть:

```text
notebook
  =
экспериментальная лаборатория

src
  =
нормальный код проекта
```

# `scripts/`

Здесь находятся программы, которые выполняют отдельные служебные действия.

## `scripts/generate_sample_data.py`

Этот скрипт генерирует учебный датасет.

Запуск:

```bash
python scripts/generate_sample_data.py
```

Он создаёт:

```text
data/raw/sample_load.csv
```

В данных есть:

- время;
- температура;
- признак выходного;
- электрическая нагрузка.

Причём данные созданы не полностью случайно.

В нагрузку специально заложены закономерности:

- утренний пик;
- вечерний пик;
- различие будней и выходных;
- зависимость от температуры;
- случайный шум.

Поэтому тебе есть что искать статистически.

### Зачем вообще генерировать данные?

На первой неделе наша цель — освоить инструменты.

Если сразу взять огромный настоящий энергетический датасет, можно несколько часов потратить только на:

- формат;
- кодировку;
- пропуски;
- разные временные зоны;
- непонятные столбцы.

Синтетические данные позволяют сначала спокойно разобраться с методами.


## `src/energy_ml/features.py`

Здесь находится код создания **признаков**.

Сейчас есть функция:

```python
add_calendar_features(...)
```

Она получает timestamp и создаёт:

```text
hour
day_of_week
month
is_weekend
```

Например:

```text
2026-10-03 12:00
```

превращается примерно в:

```text
hour = 12
day_of_week = 5
month = 10
is_weekend = 1
```

Это называется **feature engineering**.

Позже здесь появятся, например:

```text
lag_1
lag_24
lag_168
rolling_mean_24
rolling_std_24
```

Это уже будут очень полезные признаки для прогнозирования нагрузки.

# `tests/`

Здесь находятся автоматические тесты.

## `tests/test_features.py`

Он проверяет функцию:

```text
add_calendar_features()
```

Например мы заранее знаем:

```text
3 октября 2026 = суббота
```

значит:

```python
is_weekend == 1
```

Тест автоматически проверяет это.

Запуск:

```bash
pytest -q
```

### Зачем тестировать такую маленькую функцию?

Потому что сейчас она маленькая.

Через несколько месяцев проект может иметь тысячи строк кода.

Если потом ты поменяешь feature engineering и случайно сломаешь старую логику, тест сообщит об этом сразу.

# `.gitignore`

Файл объясняет Git, **что не нужно отправлять в репозиторий**.

Например:

```text
.venv/
__pycache__/
.idea/
data/raw/*
data/processed/*
```

### Почему не хранить `.venv`?

Потому что виртуальное окружение может занимать сотни мегабайт и легко восстанавливается через:

```bash
pip install -r requirements.txt
```

### Почему пока не храним датасеты?

Потому что данные:

- могут быть очень большими;
- иногда могут содержать чувствительную информацию;
- обычно имеют отдельный источник хранения.

Код должен уметь их получить или создать.

# Как всё работает вместе

На первой неделе workflow будет выглядеть примерно так:

```text
scripts/generate_sample_data.py
            ↓
 data/raw/sample_load.csv
            ↓
 notebooks/01_eda.ipynb
            ↓
 обнаружили полезные преобразования
            ↓
 src/energy_ml/features.py
            ↓
 tests/test_features.py
            ↓
 pytest
            ↓
 GitHub Actions
```

А когда появится первая ML-модель:

```text
raw data
   ↓
cleaning
   ↓
feature engineering
   ↓
processed data
   ↓
train / validation
   ↓
model
   ↓
metrics
   ↓
analysis
```

# Главное правило: куда писать новый код?

Если ты не уверен, используй такую схему.

## Я просто исследую данные

Пиши в:

```text
notebooks/
```

## Я написал функцию, которую хочу использовать много раз

Переноси в:

```text
src/
```

## Я хочу проверить, что функция работает правильно

Пиши:

```text
tests/
```

## Я хочу выполнить отдельную техническую команду

Например скачать или подготовить данные:

```text
scripts/
```

## Я хочу сохранить описание, решение или план

Пиши:

```text
docs/
```

## Это данные

```text
data/
```

# Что будет добавляться позже

Проект будет расти постепенно. Не нужно создавать всё заранее.

Пример возможной будущей структуры:

```text
src/energy_ml/
├── data.py
├── features.py
├── metrics.py
├── models.py
├── training.py
└── validation.py

models/
configs/
reports/
```

Но эти папки появятся **только когда действительно понадобятся**.

Мы специально не создаём огромную «взрослую архитектуру» заранее: задача проекта — чтобы ты понимал происхождение каждого файла.
